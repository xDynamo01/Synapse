## What the current code does

### Chat composer capture flow

`ChatComposer.tsx` now probes the environment before starting capture:

- `navigator.mediaDevices`
- `navigator.mediaDevices.getUserMedia`
- `window.MediaRecorder`
- supported MIME types:
  - `audio/webm;codecs=opus`
  - `audio/webm`
  - `audio/ogg;codecs=opus`
  - `audio/wav`
- microphone permission state via `navigator.permissions.query({ name: "microphone" })` when supported

It then attempts capture in three steps:

1. stricter audio constraints
2. relaxed constraints

## Hypotheses discarded

### 1. Backend STT provider regression

Discarded.

Evidence:

- release backend `POST /api/audio/transcribe` succeeds;
- `GET /api/voice/providers` exposes `faster_whisper` as available;
- `TranscriptResult` is returned from the packaged release backend.

### 2. Missing release packaging / missing ONNX asset

Discarded for the current regression.

Evidence:

- the earlier `silero_vad_v6.onnx` packaging problem was fixed;
- the current release bundle can transcribe again.

### 3. Tauri capability / permission bridge issue

Unlikely as the root cause.

Evidence:

- current failure is an `OverconstrainedError`-style microphone settings failure, not a Tauri permission denial;
- Tauri capabilities only cover window controls here;
- the capture path is using browser APIs directly.

### 4. Contract break in `types/contracts.ts` or `backend/synapse/api/routes.py`

Discarded.

Evidence:

- the backend route contract is intact;
- isolated backend transcription works;
- no contract mismatch blocks the backend response.

### 5. AppData cache / stale voice settings

Not the primary blocker.

Evidence:

- current persisted voice settings are:
  - `provider_id: null`
  - `device_id: null`
  - `enabled: true`
- that means the current failure is not explained by a stale selected device id.

## Root cause probable

The regression is in the frontend microphone startup path, not the backend STT pipeline.

The specific failure surface is:

- `E:\Projetos\Synapse\frontend\src\components\chat\ChatComposer.tsx`

The capture flow there now tries strict `getUserMedia` audio constraints first. On Tauri/WebView, this is the most likely source of the visible failure:

- `OverconstrainedError`
- message surfaced to the user as:
  - `As configurações do microfone não puderam ser atendidas.`

The same basic capture pattern also exists in:

- `E:\Projetos\Synapse\frontend\src\modules\VoiceModule.tsx:120-160`

That makes the issue a shared frontend capture-risk pattern, but the current user-facing failure is coming from the chat composer entry point.

## Minimum recommended correction

Do not add another workaround layer.

The smallest defensible fix is:

1. use `audio: true` as the default capture path in the chat composer;
2. keep strict device/audio constraints only as an optional fallback when the device is explicitly selected and known to be supported;
3. centralize capture probing into a single shared helper used by both chat and Voice settings so the behavior does not diverge again;
4. keep the backend and Faster-Whisper untouched.

That keeps the failure surface in one place and avoids piling frontend-specific capture heuristics on top of a healthy backend.

## Final conclusion

The current Voice regression is a frontend microphone capture issue.

It is not caused by:

- Faster-Whisper packaging
- `/api/audio/transcribe`
- Tauri backend launch
- backend contracts
- AppData cache corruption

The evidence points to the browser/WebView `getUserMedia` constraints path in the chat composer, with the same pattern mirrored in the Voice settings surface.
