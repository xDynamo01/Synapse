# Synapse 0.3 Program Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use

**Goal:** Reconstruct Synapse 0.3 as clean-room, independently testable vertical
slices without importing runtime code or state from 0.2.

**Architecture:** A headless modular Synapse Core owns identity, memory,
missions, Skills, models and tools. An Electron/React desktop client provides
Assistant, Workspace/CLI and Swarm views through stable versioned contracts.
Capability plans remain separate and integrate only through accepted contracts.

**Tech Stack:** Electron, React and TypeScript for the desktop client; a local
headless Core and versioned cross-language contracts; final Core runtime,
transport, persistence and model/audio adapters are selected by the foundation
decision gates before product scaffolding.

**Spec:** `docs/specs/2026-11-06-synapse-0.3-clean-room-design.md`

## Global Constraints

- No runtime source, build output, database, environment or configuration from
  0.2 or the archived pre-clean-room attempt may enter the new runtime.
- A.R.T.E.M.I.S. is the only permanent agent.
- All AI, memory, RAG and voice inference is local.
- Windows 11 x64 on the owner's current machine is the first operational target.
- Shared contracts and domain logic build and test on Windows, Linux and macOS.
- Linux and macOS remain below `VALIDATED` until tested on physical hardware.
- Swarm requires separate user acceptance and stays independent from MoM.
- Skills and models never grant authority; Core enforces mission contracts.
- Every slice has negative tests, real composition proof, independent QA,
  reproducible evidence and rollback proportional to risk.
- Public Git history contains no secrets, personal data or runtime state.

## Review Focus

- A passing mock must never raise a capability above `TESTED`.
- A disconnected or restarted client must not create a second authoritative Core.
- A model, Skill or web page must not expand an approved mission contract.
- A project reference must retrieve only authorized contextual memory.
- Resource exhaustion must degrade or stop safely, never overcommit silently.

## Plan Rules

- [ ] Each row receives a focused specification before its implementation plan.
- [ ] Each plan names exact files, public interfaces, tests and evidence paths.
- [ ] Product scaffolding begins only after Plan 00 decisions are accepted.
- [ ] A later plan may consume only interfaces published by an earlier plan.
- [ ] A failed gate blocks dependents; it does not produce a compatibility shim.
- [ ] Each completed slice is reviewed against the architecture and this roadmap.
- [ ] Shared changes land on `0.3`; platform branches contain release-only work.
