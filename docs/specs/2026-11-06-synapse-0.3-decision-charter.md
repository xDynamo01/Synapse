# Synapse 0.3 Decision Charter

Status: `APPROVED — BINDING`

Date: 2026-11-06. Owner-approved amendment: 2026-11-09.

## Owner-approved amendment — 2026-11-09

The owner selected a Rust native application and device integration with Python
for local AI, replacing the Electron/React/Node/TypeScript product direction.
Affected decisions: PL-001 (replaced below) and PL-006 (added below). Headless
Core, stable contracts, privacy, voice, memory, Skills and independent MoM/Swarm
requirements remain binding. This is approved product intent, not measured
approval of a native UI crate, toolchain version or Rust/Python boundary.

Migration impact: Gate 00 is **BLOCKED / REOPENED**; the Electron Plan 01
specification and plan are **SUPERSEDED / NOT EXECUTABLE**. Preserve experiment
code, locks and receipts as historical evidence, with no product dependency or
scaffolding authority. ADR 0001's Python evidence remains; its Node/client
selection is superseded. ADR 0002's Node/Python results are historical and gRPC
is a candidate pending real Rust/Python proof. ADR 0003 storage evidence remains
subject to the selected authoritative owner and binding. Execute the
[foundation revalidation plan](../superpowers/plans/2026-11-09-rust-python-foundation-revalidation.md)
before replacing Plan 01 or creating product scaffolding.

## 1. Purpose and authority

### Owner-approved delivery amendment — integrated backend first, 2026-11-09

The owner approved building the real coherent backend now, followed by the
native frontend consuming its contracts. This supersedes the earlier requirement
to complete native-UI feasibility or all experimental Gate 00 lanes before any
product source may exist. Historical Gate 00 remains incomplete; its receipts
must not be relabelled PASS to justify this new delivery order.

Rust owns the headless Core, contracts, mission/effect enforcement, permissions
and authoritative persistence. Python provides supervised local AI capabilities;
it never becomes a second authority or storage writer. The native frontend is
deferred and cannot block backend implementation. Platform/device/voice/browser
validation remains mandatory before those capabilities become OPERATIONAL.

Each backend domain is integrated through one composition root and versioned
API/CLI. Internal implementation tasks do not create independent product
architectures. Missing model/device/browser dependencies must return explicit
capability errors, never synthetic successful output. Experiments remain
evidence only. All clean-room, local AI, memory, authorization and QA decisions
remain binding. See `2026-11-09-integrated-backend-design.md` in this directory.

This charter is the stable decision index for the Synapse 0.3 reconstruction.
It prevents later specifications, plans, agents or implementation choices from
quietly changing the product agreed with the owner.

Every subproject specification, implementation plan, mission brief, task review
and release gate must:

1. cite this charter by path;
2. list the decision IDs that bind its scope;
3. include tests or evidence for every applicable decision;
4. record `N/A` with a reason for reviewed decisions that do not apply;
5. stop integration when an implementation contradicts a decision.

The detailed architecture remains
`docs/specs/2026-11-06-synapse-0.3-clean-room-design.md`. If wording appears to
conflict, this charter fixes the approved intent and the architecture explains
it. A genuine conflict must be returned to the owner as a proposed charter
amendment; it cannot be resolved silently by code.

## 2. Change control

- A decision changes only through an owner-approved amendment carrying a new
  date, rationale, affected decision IDs and migration impact.
- Superseded wording remains in Git history and the replacement names the prior
  ID.
- Technical RFCs may choose an implementation only inside these boundaries.
- Measurements may prove an approach infeasible. They may produce `BLOCKED` or
  a proposed alternative, but never redefine the product automatically.
- Temporary agents, models, Skills and web content have no authority to amend
  this charter.

## 3. Clean-room and repository decisions

### CR-001 — Clean-room reconstruction

Synapse 0.3 is rebuilt from zero. Synapse 0.2 and the archived pre-clean-room
0.3 material are reference only. Runtime source, build output, databases,
environments, configuration and operational state from them must not be copied,
linked or imported into the new runtime.

### CR-002 — Historical preservation

The old 0.3 preparation is preserved on `archive/0.3-pre-cleanroom`. Version
0.2 remains immutable historical reference. A later data migration requires a
separate audited tool and approved mission; it never permits old runtime code.

### CR-003 — Canonical branches

`0.3` is the clean-room integration source of truth. Mission branches/worktrees
are temporary and isolated. `platform/windows`, `platform/linux` and
`platform/macos` contain only build, packaging and release stabilization.
Reusable behavior is developed on or returned to `0.3`; platform branches must
not become divergent products.

### CR-004 — Public repository hygiene

The repository may remain public. Credentials, personal information, raw audio,
runtime state, authenticated sessions and secret-bearing logs never enter Git.

## 4. Product identity and experiences

### PX-001 — One permanent identity

A.R.T.E.M.I.S. is the only permanent agent and remains the same identity across
models, clients, projects and modes. Models are capabilities, not identities.

### PX-002 — Two primary experiences

The product has an Assistant experience for natural voice/chat interaction and
a Workspace/CLI experience for universal project creation. They share one Core,
identity, memory policy and mission system.

### PX-003 — Assistant visual language

The conversation surface is transparent and only chat bubbles remain visible.
The central Presence is a real audio-reactive animation: restrained idle
breathing, wake acknowledgement, microphone-driven listening glow,
processing motion, TTS-output-driven speaking expansion and immediate
interruption response.

### PX-004 — Workspace visual language

Workspace is terminal-first. Its Context Rail is genuinely collapsible and the
terminal expands when it closes. The rail shows active Workspace/project,
mission contract, artifacts, QA and resources without becoming the main canvas.

### PX-005 — Swarm visual language

An active Swarm uses the multi-terminal grid reference with visible temporary
agent role, state, actions and evidence. The normal Workspace must not look like
an always-active Swarm.

### PX-006 — Universal project scope

Workspace is not limited to software. It supports software, games, research,
documents, design, media, automation and future domains through Skills.

## 5. Voice and translation decisions

### VO-001 — Wake word and listening

The spoken wake word is the configured agent name; for this installation it is
“Artemis”, displayed as `A.R.T.E.M.I.S.`. When enabled, only the local Device
Bridge and wake detector process the pre-activation stream. The minimum rolling
buffer is continuously discarded and never reaches STT, models, memory or the
network before activation.

### VO-002 — Fixed original feminine voice

A.R.T.E.M.I.S. uses one original feminine identity: soft, warm, calm and
slightly authoritative. It may draw on general cinematic qualities but must not
clone or imitate a real performer.

### VO-003 — Cross-language identity

Installed and validated languages preserve the same perceived voice identity.
The first Windows operational gate requires Brazilian Portuguese and US English.
Additional languages are capability packs and are never claimed operational
before end-to-end validation.

### VO-004 — Normal language behavior

In ordinary conversation A.R.T.E.M.I.S. detects the language used and answers
in that language.

### VO-005 — Persistent bidirectional Translator

An explicit command starts Translator mode and it remains active until a stop
control or spoken exit command. Every detected turn is translated automatically:
the owner’s language to the requested language and a second speaker’s requested
language back to the owner. The system must separate speakers, manage turns and
prevent its own TTS from being retranslated.

### VO-006 — Audio retention

Raw audio is not persisted by default. A saved chat may keep transcript and
translation under the chat policy.

## 6. Memory and history decisions

### ME-001 — One memory system

Synapse has one canonical memory system with logical context partitions, not
separate “assistant memory” and “project memory” products.

### ME-002 — Canonical context, not transcript copies

Memory is concise, typed, versioned canonical context. Chat history restores an
exact conversation; mission evidence stores execution; RAG retrieves sources.
These stores may contribute evidence but are not interchangeable.

### ME-003 — Automatic writing and lazy reading

Durable memory writing and consolidation are automatic. Reading is lazy and
reference-driven: project memory is loaded when the user references that
project, selects it as active context or authorizes it in a mission. Presence
does not preload every project.

### ME-004 — Failure and knowledge lifecycle

Failed attempts remain mission evidence unless they establish durable knowledge
such as a reproduced issue, proven root cause, validated recovery, constraint or
decision. Promoted knowledge is versioned; resolved and superseded records are
retained rather than silently erased.

### ME-005 — Cross-context boundary

Retrieval does not authorize promotion. Global memory or global Skills may
receive only generalized behavior or constraints after project-specific content,
secrets and personal data are excluded and cross-context evidence exists.

## 7. Missions, authority and integration decisions

### MI-001 — Turn versus mission

Simple conversation, memory queries and non-persistent actions may remain turns.
Multi-step work, tools, background execution, writes or external effects become
missions.

### MI-002 — One authorization per immutable scope

A.R.T.E.M.I.S. converts natural language into a versioned mission contract. The
owner approves once, after which every declared action may execute autonomously.
Scope, target, destination, destructive effect or rollback expansion requires a
new contract revision and approval; already-declared actions do not request
repeated approval.

### MI-003 — Human authority and Core enforcement

Only the authenticated human owner may approve, revise, revoke or
discretionarily cancel a mission. Core must automatically halt on revocation,
failed gates, exhausted budgets, policy violations, stop conditions or safety
invariants. Enforcement may reduce authority but never create or expand it.

### MI-004 — Pre-authorization limit

Before approval, Core may perform only bounded local preflight needed to draft
the contract: selected Workspace identity, metadata, capability catalogues,
resource estimates and target existence. It may not alter files, execute project
code, access accounts/secrets, browse/download or inspect unrelated content.

### MI-005 — Irreversible and external effects

An irreversible or externally visible action is allowed only when its exact
effect, destination and lack of rollback are conspicuous in the approved
contract. Feasible staging and QA occur first. A changed effect requires a new
revision, not a surprise final confirmation.

### MI-006 — Isolated work and automatic integration

Development missions use isolated branches/worktrees. Independent QA validates
the exact proposed artifact. Passing work integrates automatically and receives
post-integration regression; failure rolls back where possible. Non-Git work
uses a staged artifact, transactional replacement or declared lack of rollback.

### MI-007 — Independent QA without forced Swarm

Independent QA is a role and isolation boundary, not automatically a Swarm. A
single disposable validator may review an ordinary mission using separate
context, criteria and deterministic evidence. Semantic review should use a
different model/configuration/seed when resources permit; unsupported model
self-validation is insufficient.

## 8. Skills decisions

### SK-001 — Skills provide domain expertise, not authority

Skills make Workspace domain-general and declare triggers, inputs, outputs,
tools, permissions, dependencies, quality criteria, compatibility, provenance
and limits. They never grant permissions; mission contracts and the Tool Broker
remain authoritative.

### SK-002 — Autonomous discovery inside mission scope

A.R.T.E.M.I.S. may discover, inspect, quarantine-test and install a missing Skill
through the internal browser when those actions are declared in the mission.
Origin, license, scripts and dependencies must be audited first.

### SK-003 — Evidence-driven Skill evolution

The active Skill version is immutable during a mission. Evidence may create a
descendant with lineage, diff, rationale and benchmark. Isolated tests and
independent QA precede automatic promotion; regression triggers rollback.

### SK-004 — Project-first promotion

Evolution begins as a Workspace/project variant. It becomes global only after
cross-context evidence proves generality and project/private content is removed.
Evolution cannot silently add dependencies or broaden permissions.

## 9. MoM and Swarm decisions

### MM-001 — MoM is permanent and local

Mixture of Models is the permanent local cognitive orchestration. The user
interacts with A.R.T.E.M.I.S., while Router, Registry, Planner, Scheduler,
Lifecycle Manager and Validators retain separate responsibilities.

### MM-002 — No visible Responsive/Economical product modes

Resource behavior is adaptive inside lifecycle management. Advanced missions
may set preferences or limits, but the product does not expose two simplistic
global modes named Responsive and Economical.

### SW-001 — Swarm is separate from MoM

Swarm is a temporary regime with two or more cooperating temporary agents under
one plan, concurrently or sequentially. Multiple models used by ordinary MoM,
voice, embeddings or validation do not by themselves form a Swarm.

### SW-002 — Swarm always requires acceptance

Swarm starts only through a direct owner request or a Planner recommendation
that explains roles, models, resources, benefit and risk and is then accepted by
the owner. Planner judgment alone cannot activate it.

### SW-003 — Temporary agents and evidence

A.R.T.E.M.I.S. is the sole permanent agent. Swarm agents receive minimal
context, bounded permissions, Skills, budgets and termination criteria. They
cannot write canonical memory directly. They, their permissions and model
reservations are removed after completion; compact durable evidence remains
after the recovery window.

### SW-004 — Resource-safe degradation

Swarm never silently overcommits the machine. If reservations do not fit, the
Planner offers fewer agents, sequential work or an ordinary non-Swarm mission
with revised cost and expected quality for owner acceptance.

## 10. Browser, tools and security decisions

### SE-001 — Local-first with a controlled internet boundary

Core remains useful offline. Authenticated internet use occurs through a
controlled internal browser/network boundary. AI inference is not silently sent
to third-party cloud providers.

### SE-002 — Authenticated sessions with opaque credentials

Browser sessions may remain authenticated. Credentials live in encrypted
platform storage and are exposed to models, prompts, memory and logs only as
opaque scoped handles, never plaintext.

### SE-003 — Autonomous browsing inside the contract

A.R.T.E.M.I.S. may navigate, read, click, download or submit autonomously only
inside the approved mission. Manual user browsing is not a mission action, but
still uses the protected profile. Agent action is always brokered and receipted.

### SE-004 — Web and download distrust

Web content and retrieved documents are untrusted. They receive no automatic
local file, clipboard, memory, secret or tool access. Downloads are quarantined,
typed, hashed and scanned and are never auto-executed.

### SE-005 — CLI and subprocess containment

Workspace CLI is a client surface, not an authority bypass. Agent commands,
shells, build/test processes and executable Skills are mediated by Core and
inherit no more capability than their invocation. Read-only direct user commands
may use a visible Workspace grant; persistent, executable, networked or account
effects become missions.

### SE-006 — Security before sensitive boundaries

Formal threat models precede implementation of browser, tool, credential,
remote-access and self-evolving-Skill boundaries. Enforcement lives in Core and
OS/device boundaries, never only in prompts.

## 11. Deployment and platform decisions

### PL-001 — Headless Core and independent clients

Authoritative state and execution live in a headless modular Core, independent
of the native Rust desktop client. Rust owns the native application and device
integration; Python supplies local AI capabilities. Core and client are
co-located initially and communicate through stable versioned contracts. The
Rust Core is the authoritative owner and sole persistence writer; Python runs
as supervised local AI workers. Integration and failure evidence remain required
for each deployed worker boundary; the UI never becomes authoritative.

### PL-002 — Future personal data center

The same Core must later move to a personal server such as a Mac Studio while
desktop and mobile clients connect remotely through authenticated encrypted
channels, without rewriting domain contracts.

### PL-003 — Modular monolith first

Core begins as a modular monolith, not microservices. Internal boundaries must
permit later deployment separation without paying that operational cost now.

### PL-004 — Three platforms, truthful status

Windows, Linux and macOS are developed together. Windows is first operational.
Linux/macOS may be implemented and automatically tested before hardware exists,
but cannot be labelled validated or operational until real audio, secure
storage, models, installer/update and recovery paths pass on physical hardware.

### PL-005 — Initial background behavior

Closing the desktop window may leave an explicitly enabled tray/background host.
The first release does not listen with no logged-in user. Locked-session
listening is disabled by default and requires a separate visible setting if
later supported.

### PL-006 — Rust and Python product only

Product application code uses Rust and Python only: native Rust UI, application
and device integration, with Python for AI. JavaScript/TypeScript, Node,
Electron, React, Tauri and a web-rendered application UI are excluded from the
product stack. Historical JS/TS experiments may remain as archived evidence;
their runtimes, build tools and generated clients cannot become product
dependencies. Existing documentation/check tooling does not authorize another
product language.

Select the native UI crate, exact Rust/Python versions, communication boundary,
authority/storage ownership and packaging only after measured, reproducible
cross-platform decision gates. An internal browser may render untrusted remote
web content, including site JavaScript, in its isolated engine; it cannot supply
the application UI or require Synapse-authored JavaScript application/bridge
code. If no candidate meets that constraint, report BLOCKED rather than silently
introducing Tauri, a web UI or another language.

## 12. Quality and evidence decisions

### QA-001 — Granular capability status

Status is `IMPLEMENTED`, `INTEGRATED`, `TESTED`, `VALIDATED` or `OPERATIONAL`.
Results are `PASS`, `FAIL`, `BLOCKED` or `NOT RUN`. Mocks, static wiring and model
claims never prove operation.

### QA-002 — Vertical-slice evidence

Each slice needs contract and negative tests, deterministic checks where
possible, real composition, independent QA, active-runtime validation when
applicable, reproducible evidence, post-integration regression and rollback
proof proportional to risk.

### QA-003 — Exact artifact validation

QA and evidence identify the exact commit/artifact, environment, commands,
results, limitations and integration decision. Testing a substitute, isolated
mock or different build does not validate the artifact delivered to the user.

## 13. Mandatory stage compliance block

Every future subproject specification and implementation plan must contain this
block, filled with exact IDs:

```markdown
## Decision Charter Compliance

**Charter:** `docs/specs/2026-11-06-synapse-0.3-decision-charter.md`

**Binding decisions:** `ID`, `ID`, ...

| Decision | Implementation obligation | Test/evidence owner |
|---|---|---|
| ID | Exact obligation for this stage | Exact task or gate |

**Reviewed but not applicable:** `ID — reason`

**Proposed deviations:** None. Any non-empty entry blocks implementation until
the owner approves a charter amendment.
```

Task briefs inherit the compliance block from their plan. Task reviewers must
report a specification failure when a binding decision lacks implementation or
evidence, even if the task’s code otherwise works.
