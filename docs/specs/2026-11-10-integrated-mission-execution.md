## One integrated pipeline

Core owns the plan, immutable authorization, artifacts, runner receipts and
execution state. Python/model output proposes data only. Existing chats, memory,
Skill pins, storage, idempotency, supervised workers and artifact broker are reused.
No second database, alternate backend, frontend or Swarm is introduced.

The planner receives the owner's objective, explicit context references and an
optional exact Skill pin. It proposes bounded artifact descriptions and fixed
verification recipes. Core validates the entire result and constructs a proposed
mission contract, retaining the exact human objective. Planning does not generate
source files, execute project code, write the Workspace or approve the proposal.

One owner approval binds exact output paths, selected models/configuration,
generation/check budgets, verification recipes and rollback. Generated bytes are
not known before approval: a separately declared generation policy authorizes
candidate content only for those exact paths. Core records each candidate digest
in its private staging ledger; that does not mutate the approved contract.
The legacy exact-artifact-digest tool path remains unchanged.

After approval, code is generated into Core-private staging, then compiled/tested
inside an enforcing native Windows boundary. A separate reviewer invocation uses
the objective, sealed candidates and observed check receipts, not the generator's
self-assessment. Initial validation may reuse one resident model with separate
context and explicitly different generation settings; this is not independent
weights or proof of perfect semantic correctness. Deterministic checks are also
required; a model's claim of success cannot replace them.

Only a Core-sealed QA-accepted candidate may enter the existing artifact broker
under this generation policy. It remains constrained to the approved action and
exact target, Skill declarations and captured digest. Passing artifacts integrate
automatically, receive readback/post-integration checks, and retain durable receipts.
Rollback may remove only files created by that run whose identity and hash still
match. Altered/ambiguous targets stay reserved for recovery; never delete a user's
changed file, blindly replay an effect or restore a revoked grant.

## Initial supported project execution

Start with new, non-Git Workspace projects and bounded flat files; Python stdlib
unittest and dependency-free Rust `rustc --test` are the first fixed recipes.
The caller does not supply executable paths, shell fragments, environment or
arbitrary argv. Git/Cargo dependency/build-script workflows, package downloads,
network access and arbitrary shell require later enforcing adapters; they cannot
silently fall back to the unrestricted host.

Runner direction: native LPAC, zero network capabilities, private copies of trusted
tool assets, protected readonly source/runtime and bounded writable output/temp,
plus Job Object ownership and resource limits. Verify the suspended token before
resuming. Windows loader baseline and disposable profile storage remain documented
OS resources; this is not a literal virtual root or hard disk-quota guarantee.
Do not modify global Python/Rust/VS/SDK ACLs. Real positive and adversarial probes
must pass before reporting this capability operational. Missing assets/isolation
return explicit unavailable.

## Persistence and stopping

Mission authorization state remains separate from a durable run's execution phase.
One mission owns one sealed execution lineage. Stops/revocation persist, terminate
owned activity, prevent late results and block further effects. Restart marks
in-flight work interrupted and exposes explicit resume/recovery. Core reconciles
observed file receipts before resuming; no automatic replay of prepared writes.

No files or project code are touched before approval except the bounded metadata
preflight permitted by MI-004. Plan and job persistence in Core's existing private
store is ordinary application bookkeeping, not Workspace mutation.
