## 1. Intent

Synapse 0.3 is a clean-room reconstruction of a local-first intelligent system
centered on one persistent agent identity: **A.R.T.E.M.I.S.** The product must
combine a natural assistant experience with a universal project-creation
workspace while keeping memory, tools, models, Skills, missions and Swarm
observable and governed.

The 0.2 implementation and the archived pre-clean-room 0.3 work are reference
material only. No runtime source code, build output, database, environment or
configuration from those versions may be copied into the new implementation.

## 2. Why this reconstruction exists

The previous product accumulated overlapping responsibilities, broken
integrations, non-operational tools, unreliable Swarm execution and incomplete
conversation flows. Continuing to repair that implementation would preserve the
same accidental contracts. The new system must establish one coherent
architecture and prove capabilities through the real user path.

## 3. Goals

- Provide one continuous A.R.T.E.M.I.S. Presence independent of any LLM.
- Support two primary experiences: Assistant and Workspace/CLI.
- Operate locally without third-party AI or cloud inference.
- Select and coordinate local models through a permanent MoM architecture.
- Support universal project creation through contextual, versioned Skills.
- Allow Skills to evolve automatically from evidence without losing rollback.
- Execute complex work as approved missions with one authorization per scope.
- Integrate mission output automatically after independent QA passes.
- Use Swarm only when explicitly requested or separately accepted after a
  Planner recommendation.
- Maintain canonical, versioned and selectively retrieved contextual memory.
- Provide a controlled internal browser for authenticated internet access.
- Run locally on Windows first while keeping Core and clients portable to Linux
  and macOS.
- Permit a future personal-server topology without rewriting product contracts.

## 4. Non-goals for the initial operational release

- General proactive autonomy without a user request or approved mission.
- Third-party hosted inference as a hidden fallback.
- Multiple permanent assistant identities.
- Automatic Swarm activation without user approval.
- Literal support for every human language before it is installed and tested.
- Operational status for Linux or macOS without execution on physical hardware.
- A microservice deployment topology.
- Mobile implementation before the stable client-server contracts exist.

## 5. Anti-goals

The reconstruction is a failure if it:

- copies old runtime code into the new branch;
- presents mocks, static wiring or LLM claims as operational evidence;
- gives Skills, models or web content implicit authority;
- stores raw conversations as canonical memory;
- allows project context to leak without a reference and an authorized lookup;
- creates permanent Swarm agents or a second memory system;
- embeds the authoritative Core inside the desktop UI;
- develops three divergent operating-system implementations;
- requires repeated approvals for actions already declared in an immutable
  mission contract;
- silently expands a mission beyond its approved scope.

## 6. Constraints

- The current target machine is Windows and all initial operational validation
  occurs there.
- Core and desktop run on the same computer initially.
- The architecture must compile and be tested for Windows, Linux and macOS from
  the start.
- All model inference, wake-word detection, STT, translation, TTS, embeddings,
  memory and RAG are local.
- Internet access is explicit, observable and mediated by the controlled network
  boundary.
- The initial repository is public; secrets, personal data and runtime state
  must never enter Git.
- A.R.T.E.M.I.S. is the only permanent agent.

## 7. Approaches considered

### 7.1 Desktop-embedded Python runtime — historical, superseded

Electron would launch and own an embedded Python backend. This is fast to ship
but makes the UI lifecycle authoritative and creates a later extraction project
when a personal server is introduced.

### 7.2 Lightweight web shell / third language — historical, excluded

The original comparison considered Tauri/Rust or .NET. The owner has now selected
native Rust plus Python only. Tauri, a web application UI and third product
languages are excluded; this historical comparison is not a native UI decision.

### 7.3 Headless modular Core plus independent clients — selected

A headless Core owns identity, state and execution. A native Rust desktop client
provides Assistant/Workspace/Swarm presentation and Rust device integration;
Python supplies local AI. They are co-located initially and use stable versioned
contracts. The exact Rust/Python process or embedding split and authoritative
Core/storage owner require revalidation; the UI never owns Core authority. The
same Core can later move to a Mac Studio or another personal server without
changing its domain contracts.

Native UI crate, exact versions, transport and packaging remain unselected until
the reopened foundation gates pass. No Electron decision is inherited.

## 8. Top-level topology

```text
Current single computer

┌──────────── Native Rust Desktop Client ────────┐
│ Presence UI · Chat · Voice · Workspace · Swarm │
│ Internal browser view · Device capabilities    │
└──────────────────────┬─────────────────────────┘
                       │ authenticated local contract
┌──────────────────────▼─────────────────────────┐
│          Headless Synapse Core                 │
│ A.R.T.E.M.I.S. · Memory · Missions · Skills    │
│ MoM · Planner · Scheduler · Python AI · Tools  │
│ Browser boundary · QA · Evidence · Swarm        │
└────────────────────────────────────────────────┘
```

Future clients use the same contracts over an authenticated encrypted channel.
Remote listening is disabled by default.

Rust handles native application/device integration; Python handles local AI.
The drawing expresses logical boundaries, not a selected FFI/process topology.
R2/R3 revalidation must name the sole authority/storage owner and prove lifecycle
and packaging. Remote browser content is isolated and cannot implement the UI
or require Synapse-authored JavaScript application/bridge code (PL-006).

The desktop application is the initial client and contains both Assistant and
Workspace/CLI experiences. Closing its main window may leave an explicitly
enabled tray/background audio host active. The initial release does not listen
while no user is logged in. Listening on a locked session is disabled by
default and, if later supported by the operating system, requires a separate
visible user setting.

## 9. A.R.T.E.M.I.S. Presence

A.R.T.E.M.I.S. is a persistent system identity, not a model, prompt, window or
Workspace. Changing model, client or active project does not change the
Presence. Its durable identity and state live in Core.

The wake word is the configured agent name. For this installation the display
name is `A.R.T.E.M.I.S.` and the spoken wake word is "Artemis". A later rename
must update and recalibrate the local detector.

The initial Presence is reactive:

- local wake-word detection is always available when enabled;
- audio before activation is neither persisted nor sent to inference;
- activation opens a voice turn;
- global microphone state is visible and can be disabled;
- proactive autonomy is a future policy, not an initial behavior.

Before activation, only the local audio Device Bridge and wake-word detector may
process the microphone stream. They keep the minimum rolling in-memory buffer
required by the detector and discard it continuously. STT, models, memory and
network components receive no audio until activation.

## 10. Product experiences

### 10.1 Assistant

Assistant mode combines voice and text. The visual center is an animated
Presence that reacts to real pipeline state:

| State | Visual behavior |
|---|---|
| Idle | slow restrained breathing |
| Wake detected | short acknowledgement pulse |
| Listening | glow driven by normalized microphone level |
| Processing | orbital activity without simulated speech |
| Speaking | core expansion driven by actual TTS output amplitude |
| Interrupted | immediate transition back to listening or idle |
| Error | distinct, calm and accessible error state |

Only normalized audio levels and state events reach the renderer. Raw audio
stays in the local audio pipeline.

The conversation surface has no opaque Conversation Log panel. Chat bubbles
float over the continuous background. The full saved chat history is available
on demand. Chat history, not memory, restores a specific conversation.

Visual reference: `docs/assets/presence-voice-chat-reference.png`.

### 10.2 Workspace/CLI

Workspace is a universal project-creation environment, not only a software IDE.
It supports software, games, research, documents, design, media, automation and
future domains through Skills.

The CLI is a terminal surface of the desktop client, not an authority bypass.
Shells, build and test subprocesses, executable Skills, filesystem access and
network access are capabilities mediated by Core's Tool Broker and the active
mission contract. A child process inherits no broader authority than the tool
invocation that created it. The minimum enforcement design uses OS process
isolation, scoped working roots, brokered secret handles, network policy and
authoritative receipts; prompt instructions alone are never containment.

Read-only commands typed directly by the user may run under a visible,
Workspace-scoped interactive session grant. A typed command that writes,
executes project code, uses an account, reaches the network or can persist an
effect is converted into a mission contract before execution. Agent-generated
commands never inherit authority merely because they appear in the terminal.

The selected normal-state layout is terminal-first. A dominant terminal is
paired with a collapsible Context Rail showing the active Workspace, project,
mission contract, changed artifacts, QA state and resource information. When
collapsed, the terminal expands and only a reopen affordance remains.

Visual target: `docs/assets/workspace-context-rail-selected.png`.

### 10.3 Swarm

When Swarm is active, the operational area switches to a grid of temporary
agent terminals. Each panel shows role, state, actions and evidence. The Context
Rail may remain collapsed to maximize the grid.

Visual reference: `docs/assets/swarm-active-grid-reference.png`.

## 11. Voice and translation

A.R.T.E.M.I.S. uses one fixed, original feminine voice: soft, warm, calm and
slightly authoritative. The direction is inspired by the intimacy and restraint
of cinematic conversational assistants, but must not clone or imitate a real
performer.

The same voice identity must remain consistent across installed and validated
languages. Language support is an extensible catalogue; unsupported or
unvalidated languages are not reported as operational.

The first Windows operational gate requires Brazilian Portuguese and US
English for conversation and bidirectional translation. Additional languages
are capability packs and become operational only after the same-identity voice,
STT, translation and end-to-end fixtures pass. This is an acceptance floor,
not a permanent two-language limit.

Normal conversation detects the input language and responds in that language.
An explicit command starts persistent bidirectional Translator mode:

```text
user language A -> target language B
second speaker language B -> user language A
```

Every detected turn is translated until the user presses Stop or speaks an exit
command. The mode uses language identification, VAD, speaker separation,
turn-taking and echo cancellation so A.R.T.E.M.I.S. does not retranslate its own
TTS output. Original and translated text are visible. Raw audio is not persisted
by default; a saved chat may retain transcript and translation.

## 12. Unified contextual memory

Synapse has one memory system. Records use a common schema and are partitioned
by logical owner/context rather than implemented as unrelated memory products.

Memory is a concise, versioned canonical representation of a context. It is not
a raw message history. Chats store conversations. Missions store execution.
RAG retrieves source passages. These systems can contribute evidence but do not
become interchangeable.

A canonical record includes at least:

- stable ID;
- logical context and owner;
- type and content;
- provenance and evidence references;
- status, version and timestamps;
- relations and access policy.

Writing is automatic. Consolidation classifies, scopes, deduplicates, compares,
versions and indexes durable information. Contradictions are not silently
merged.

Reading is lazy and reference-driven. The Presence does not preload every
project. If the user references a project from a general conversation, Core
resolves that context and retrieves only relevant records. Exact conversation
continuation uses saved chat history instead.

A project lookup is authorized only by an explicit user reference, the active
Workspace/project selection, or an approved mission contract naming that
context. A project record never enters global memory merely because it was
retrieved. Cross-context promotion may retain generalized behavior or a durable
constraint only after secrets, personal data and project-specific content are
excluded and the applicable memory policy permits that derived record.

Failures stay in mission evidence by default. A reproduced issue, proven root
cause, durable constraint, validated recovery or architectural decision may be
promoted automatically as a typed canonical record. Resolved knowledge remains
versioned as `resolved` or `superseded`.

## 13. Missions and authorization

Simple conversation, memory queries and non-persistent actions remain turns.
Multi-step work, tools, background execution, file changes or external effects
become missions.

Before authorization, Core may perform only bounded local preflight needed to
draft an accurate contract: identify the selected Workspace, inspect metadata
and capability catalogues, estimate resources, and check whether declared
targets exist. It may not alter files, execute project code, access secrets or
accounts, browse the network, download dependencies, or inspect unrelated
content. Discovery that needs any of those capabilities is a separate approved
mission or an explicit first phase of the mission contract.

A.R.T.E.M.I.S. creates a versioned mission contract from the natural-language
request. The contract declares:

- objective and acceptance criteria;
- Workspace/project and allowed targets;
- tools, Skills and accounts;
- network destinations;
- allowed read, write, execute, publish and delete actions;
- data allowed to leave the machine;
- resource and time budgets;
- QA gates, rollback and stop conditions.

The user reviews and authorizes the mission once. Every declared action may then
run autonomously. Scope expansion, an undeclared destructive target, an
undeclared destination or invalid rollback creates a new contract revision and
requires new authorization. Platform or third-party confirmations are never
bypassed.

Only an authenticated human owner can approve, revise, revoke or
discretionarily cancel a mission; A.R.T.E.M.I.S., models, Skills and web content
cannot. Core must still halt execution automatically when a contract stop
condition, revocation, policy boundary, budget, failed gate or safety invariant
requires it. Such enforcement can reduce authority but never create or expand
it. Routine missions may be approved from a paired client after an interactive
user-presence check. Pairing, credential export, recovery-policy changes and
other authority-administration operations require a trusted local confirmation.
Grants can be revoked at any time, and client compromise does not transfer owner
authority.

Irreversible or externally visible actions are permitted only when their exact
effect, destination and lack of rollback are conspicuous in the approved
contract. All feasible staging and QA must pass before that effect executes.
Approval remains once per mission: there is no surprise final confirmation, but
an undeclared or materially changed effect requires contract revision.

## 14. Isolated development and automatic integration

Development missions use isolated branches/worktrees. Temporary implementers
cannot modify the stable branch directly. Independent QA validates the exact
commit proposed for integration.

Automatic merge and rollback apply to version-controlled project changes.
Non-Git projects use an equivalent staged artifact, backup or transactional
replacement when available; otherwise the contract must declare that automatic
integration is unavailable or irreversible. External publication is a separate
declared effect and occurs only after its pre-publication gates pass.

Independent QA is a role and isolation boundary, not automatically a Swarm. An
ordinary mission may run one disposable validator session with separate context,
inputs and pass criteria. Swarm approval is required when two or more temporary
agents cooperate under one execution plan, whether concurrently or sequentially.
Multiple local models used by ordinary MoM routing, voice, embeddings or a
validator do not by themselves constitute a Swarm.

The validator receives the proposed artifact and contract, not the implementer
chain of thought or unverified conclusions. Deterministic gates are authoritative
where available. Semantic review should use a distinct model, configuration or
seed when resources permit; reuse of the same model is acceptable only when
independent deterministic evidence or an explicitly required human review
prevents the model from validating its own unsupported claim.

If the mission contract and all gates pass, A.R.T.E.M.I.S. merges automatically
and runs a post-merge regression. A post-merge failure triggers automatic
rollback. Repeated correction cycles are bounded; uncorrected work ends as
`FAIL` or `BLOCKED` and is not integrated.

Temporary detailed logs remain until QA, acceptance and the recovery window are
complete. Durable mission evidence retains result, versions, artifacts, tests,
limitations and the integration decision.

## 15. Skills

Skills make Workspace domain-general. A Skill declares purpose, triggers,
instructions, inputs/outputs, required tools, permissions, dependencies,
templates, quality criteria, tests, compatibility, origin, version and known
limits.

Skills never grant authority. A mission contract and the Tool Broker remain the
enforcement boundary.

When a required Skill is missing, A.R.T.E.M.I.S. may discover candidates through
the internal browser, audit origin/license/scripts/dependencies, test them in
quarantine and include installation in the mission contract.

### 15.1 Evolution

Skills evolve from real evidence. The active version is immutable during a
mission. Evidence can produce a candidate descendant with a diff, rationale and
benchmark. Candidates run in isolation and face independent QA and regression
against their ancestor.

Successful versions promote automatically for future missions and roll back
automatically on regression. Evolution cannot silently broaden permissions or
add unaudited dependencies.

Global descendants contain only generalized instructions and measurements.
Project artifacts, secrets, personal information and identifying examples stay
in their owning context. Promotion requires both isolation tests and evidence
that the candidate works outside the originating project; otherwise it remains
a project/Workspace variant.

Evolution is hierarchical:

```text
base Skill
├── global A.R.T.E.M.I.S. adaptation
└── Workspace/project variant
       └── cross-context evidence -> global candidate
```

This permits adaptation to A.R.T.E.M.I.S.' environment and work rhythm without
overfitting every project to one local case.

## 16. MoM and local model runtime

MoM is the permanent cognitive orchestration architecture. The user interacts
with A.R.T.E.M.I.S., not model identities. All inference providers are local.

Responsibilities remain separated:

- Neural Router selects capabilities and execution paths.
- Model Registry records capability, modality, compatibility and measured
  behavior independent of commercial model names.
- Planner defines complex task DAGs and acceptance criteria.
- Scheduler coordinates readiness, dependencies, cancellation and recovery.
- Lifecycle Manager loads, reuses, reserves and unloads models.
- Validators check deterministic criteria first and semantic criteria when
  required.

The visible Responsivo/Econômico modes are removed. Lifecycle management is
adaptive and considers latency needs, RAM/VRAM, resident models and mission
limits. Advanced mission preferences may favor speed or resource conservation.

## 17. Swarm

Swarm is separate from MoM and from ordinary task concurrency. It is a temporary
execution regime in which two or more temporary agents cooperate under one plan,
whether concurrently or sequentially. A Swarm may reserve multiple resident
models, but multi-model MoM operation without cooperating temporary agents is
not a Swarm.

Swarm starts only when:

1. the user requests it directly; or
2. the Planner recommends it, explains roles/resources/benefit, and the user
   accepts it before mission execution.

If required model or hardware reservations do not fit, Swarm does not
overcommit the machine. The Planner offers a smaller agent set, sequential
execution or an ordinary non-Swarm mission with revised cost and expected
quality. A materially revised regime is shown to the user before execution.

A.R.T.E.M.I.S. is the only permanent agent. Temporary agents receive roles,
minimal contextual projections, bounded permissions, Skills, model assignments,
budgets and termination criteria. They cannot write canonical memory directly.

After completion or cancellation, temporary agents are deleted, model
reservations released and permissions revoked. Temporary logs preserve actions,
successes, failures and tool receipts long enough for A.R.T.E.M.I.S. or a
temporary independent QA agent to evaluate integration. Only compact durable
mission evidence remains afterward.

## 18. Internal browser and network boundary

Core remains useful offline. Authenticated internet access occurs through a
controlled browser/network boundary when a mission needs it.

The boundary provides:

- isolated profiles by Workspace or mission;
- encrypted session storage;
- opaque credential handles unavailable to models, prompts, memory and logs;
- page-content isolation and prompt-injection defenses;
- no automatic local-file, clipboard or memory access;
- task-scoped domains, duration and budgets;
- download quarantine, type/hash/signature/malware checks;
- no automatic execution of downloaded software;
- SSRF and local-network protections;
- provenance for web and RAG sources;
- complete network receipts and a global stop control.

Read/navigation can be autonomous. Reversible writes and sensitive actions may
also execute after they are explicitly declared in the one-time mission
contract. Undeclared transmission or effect requires a revised contract.

Manual browsing performed directly by the user is not a mission action, but it
still uses the protected browser profile and credential boundary. Once
A.R.T.E.M.I.S. reads, clicks, downloads or submits on the user's behalf, the
operation is brokered and must be covered by a mission contract.

## 19. Security boundaries

- Enforcement lives in Core and device boundaries, never only in prompts.
- Web content, retrieved documents and model output are untrusted data.
- Credentials use platform secure storage and are exposed only as handles.
- Clients and Device Bridges have explicit identities and scoped capabilities.
- Client compromise must not imply unrestricted Core authority.
- Workspace/project context is filtered before model delivery.
- Tool execution emits authoritative receipts.
- Destructive missions require exact targets and a valid recovery strategy.
- The future remote channel requires encryption, device pairing and revocation.
- No runtime secrets or personal state enter the public repository.

A formal threat model is required before implementation of browser, tool,
credential, remote-access or self-evolving-Skill boundaries.

## 20. Cross-platform design

Core and clients are developed for Windows, Linux and macOS together. Domain
logic cannot depend on platform APIs. Adapters own:

- Windows Service, systemd and launchd;
- DPAPI, Linux secure storage and macOS Keychain;
- CUDA/DirectML/CPU and Metal/Apple Silicon model backends;
- filesystem paths and permissions;
- audio/wake-word integration;
- installers, updates, signing and rollback;
- OS-specific Device Bridge tools.

Windows is the first `OPERATIONAL` target. Linux and macOS may reach
`IMPLEMENTED` and `TESTED` through builds and automated tests, but remain not
operational until physical-hardware validation.

The Windows baseline is Windows 11 x64 on the owner's current development
machine; exact RAM, VRAM and model budgets are recorded by the implementation
benchmark rather than guessed in this design. Every vertical slice must build
and run its platform-neutral contract tests on Windows, Linux and macOS CI where
the required runner exists. Platform branches add release-specific gates. A
Linux or macOS release cannot be labelled `VALIDATED` or `OPERATIONAL` until its
real audio, secure storage, model backend, installer/update and recovery paths
have passed on physical hardware.

## 21. Repository and release strategy

- `0.2`: immutable historical reference.
- `archive/0.3-pre-cleanroom`: preserved preparation/inventory/corrective work.
- `0.3`: clean-room integration and source of truth.
- mission branches/worktrees: temporary isolated implementation.
- `platform/windows`: Windows release stabilization only.
- `platform/linux`: Linux release stabilization only.
- `platform/macos`: macOS release stabilization only.

Shared features are never developed independently in platform branches. Reusable
fixes return to `0.3`; releases receive platform-specific tags.

The clean-room runtime starts with no automatic import of executables,
configuration, memory or operational state from 0.2 or the archived pre-clean-
room attempt. Those branches and archived documents are reference material.
Any later data continuity need requires an explicit, audited migration tool and
mission; old code is never linked into the new runtime.

## 22. Quality, evidence and status

Capability status remains granular:

- `IMPLEMENTED`: new code exists and is identified;
- `INTEGRATED`: real callers, registration and composition are proved;
- `TESTED`: relevant tests ran on a named commit/environment;
- `VALIDATED`: expected behavior was observed in an appropriate environment;
- `OPERATIONAL`: real user path, recovery and regression passed.

Results are `PASS`, `FAIL`, `BLOCKED` or `NOT RUN`. Mocks and static tests do not
prove operation.

Every vertical slice requires:

- contract and negative tests;
- deterministic validation where possible;
- integration through the real composition path;
- independent QA;
- operational test in the active client/runtime when applicable;
- documentation and reproducible evidence;
- post-integration regression and rollback proof proportional to risk.

## 23. Delivery sequence

The implementation plan will decompose these architecture gates after this
design is approved. The intended dependency order is:

1. Rust/Python foundation revalidation, then repository governance and native cross-platform skeleton;
2. headless Core lifecycle plus versioned client/event contracts;
3. desktop shell, connection/reconnection and Presence identity;
4. local conversation model with saved chats;
5. wake word, STT, fixed multilingual voice and audio-reactive Presence;
6. unified canonical memory plus reference-driven retrieval;
7. Workspace/CLI, artifacts and Context Rail;
8. mission contracts, authorization, branches and QA integration;
9. Tool Broker, Device Bridge and controlled browser;
10. Skills discovery, execution and evolutionary lineage;
11. MoM routing, lifecycle and specialized local models;
12. Swarm temporary agents and multi-model residency;
13. bidirectional Translator mode;
14. Windows packaging and operational validation;
15. Linux/macOS build and automated test stabilization;
16. clean-room reproduction, security review and release acceptance.

Each item is delivered as a working vertical slice rather than a collection of
unconnected framework modules.

## 24. Decisions intentionally left to implementation RFCs

The following are engineering selections, not unresolved product intent:

- exact Core transport and serialization after a local/remote contract spike;
- native Rust UI crate/toolchain and Python runtime pins after measured portability,
  accessibility, animation/audio and internal-browser feasibility;
- Rust/Python process/embedding boundary, sole authority/storage owner and packaging;
- persistence engine after concurrency, backup and recovery benchmarks;
- concrete local model runner adapters;
- wake-word, STT, translation and TTS model catalogue after hardware benchmarks;
- native rendering technology for the audio-reactive Presence, inside PL-006;
- exact temporary-log recovery window;
- remote networking/pairing implementation;
- mobile client toolkit;
- installer and signing services per platform.

Each selection must preserve the constraints and behavior in this design.
